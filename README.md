# DDIA 2026 — Fullstack, домашняя работа 1

Учебный проект по автоматизации мониторинга в Grafana.

## Текущее состояние

Готовы TypeScript-сервис с хранилищем в памяти, автоматический каталог `/handlers`,
сбор длительности запросов через `@prometheus-io/client` и `/metrics`,
два экземпляра одного образа, Prometheus и Grafana с автоматически созданными
источником данных и дашбордом. Генератор получает каталог работающего приложения
и создаёт по три панели на каждую ручку: latency, RPS и ошибки.

Фоновый нагрузчик обращается ко всем трём ручкам обоих экземпляров, за две минуты
повышает суммарную частоту от 2 до 30 RPS и продолжает работу до остановки стека.
Он создаёт ожидаемые ответы `400` и `404`; данные на графиках появляются после
начала нагрузки и сбора метрик Prometheus.

## Запуск

Нужен работающий Docker Desktop с Linux-контейнерами и Docker Compose v2.
Локальная установка Node.js для запуска контейнеров не требуется.

При первом запуске в новой копии проекта:

```sh
cp .env.example .env
docker compose up
```

В PowerShell команда копирования также доступна как
`Copy-Item .env.example .env`. Если `.env` уже существует, сохраняйте его:
перезаписывать текущий пароль примером не нужно.

`.env.example` содержит только демонстрационные значения для локального стенда.
Собственные учётные данные хранятся в `.env`, исключённом из Git и Docker context.
Пароль Grafana передаётся через окружение. При работе над этой локальной копией
был создан `.env` со случайным паролем; автоматическая генерация паролей не является
частью `docker compose up`. Логин и пароль можно посмотреть в своём `.env`.

| Компонент | Адрес | Примечание |
| --- | --- | --- |
| Первый экземпляр | http://localhost:8081/health | `pod-1`, `dc-1` |
| Второй экземпляр | http://localhost:8082/health | `pod-2`, `dc-2` |
| Prometheus | http://localhost:9090 | Обе цели уже настроены |
| Grafana | http://localhost:3000 | Учётные данные из `.env` |
| Дашборд | http://localhost:3000/d/items-service-overview | Девять панелей для текущего каталога |

Порты опубликованы только на локальном интерфейсе компьютера.
Первый запуск требует скачивания образов. Команда `docker compose up` собирает
приложение; второй экземпляр, генератор дашборда и нагрузчик используют тот же образ.
Сервис `dashboard-generator` запускается после готовности обоих приложений
и Grafana, сохраняет дашборд и завершается. Код завершения `0` означает успех;
ошибка получения каталога или сохранения приводит к ненулевому коду.

Сервис `load-generator` запускается после готовности обоих приложений
и успешного завершения `dashboard-generator` (`service_completed_successfully`).
Ошибка генерации дашборда не позволяет начать нагрузку.

Запуск всего стека в фоне и просмотр нагрузки:

```sh
docker compose up -d
docker compose logs -f load-generator
```

Состояние всех сервисов, включая завершившийся генератор: `docker compose ps -a`.
Логи: `docker compose logs -f`.
Остановка: `docker compose down`.

Grafana и Prometheus сохраняют состояние в Docker volumes. Изменение пароля в
`.env` после первого запуска не меняет пароль уже созданного пользователя Grafana.
Данные самого приложения находятся только в памяти и теряются при его перезапуске.

## HTTP API

Запись состоит из `id`, `name` и необязательного `description`.
Идентификатор UUID генерирует сервер. Имя должно содержать хотя бы один
непробельный символ и быть не длиннее 200 символов; описание — не длиннее 2000.
Неизвестные поля и неверные типы отклоняются с кодом `400`.

| Метод и путь | Поведение |
| --- | --- |
| `POST /items` | Создаёт запись; `201`, JSON записи и заголовок `Location` |
| `GET /items/{id}` | Возвращает запись; `200` либо `404` |
| `PUT /items/{id}` | Полностью заменяет поля записи, сохраняя id; `200` либо `404` |
| `GET /health` | Готовность приложения и значения `POD_ID`, `DATACENTER`; `200` |
| `GET /metrics` | Метрики в текстовом формате Prometheus; `200` |
| `GET /handlers` | Автоматически собранный каталог бизнес-маршрутов; `200` |

`PUT` не создаёт отсутствующую запись. Если при замене не передано `description`,
оно удаляется. Пример тела для создания и замены:

```json
{"name": "First item", "description": "Example"}
```

У экземпляров независимые хранилища: запись, созданная через порт `8081`,
недоступна через `8082`. Нагрузчик хранит отдельный пул ID для каждого экземпляра.

Проверка CRUD в PowerShell:

```powershell
$item = Invoke-RestMethod http://localhost:8081/items -Method Post -ContentType 'application/json' -Body '{"name":"First item"}'
Invoke-RestMethod "http://localhost:8081/items/$($item.id)"
Invoke-RestMethod "http://localhost:8081/items/$($item.id)" -Method Put -ContentType 'application/json' -Body '{"name":"Updated item"}'
```

## Каталог маршрутов

`GET /handlers` возвращает зарегистрированные бизнес-маршруты без необходимости
предварительно отправлять к ним запросы:

```json
{
  "handlers": [
    { "method": "POST", "route": "/items" },
    { "method": "GET", "route": "/items/:id" },
    { "method": "PUT", "route": "/items/:id" }
  ]
}
```

Модуль `src/handlers.ts` подключается непосредственно к корневому приложению
до регистрации бизнес-маршрутов. Синхронный hook
[`onRoute`](https://fastify.dev/docs/latest/Reference/Hooks/#onroute) сохраняет
пары «метод + шаблон пути» в отдельном для каждого приложения `Map`, устраняя
дубликаты. Регистрация с массивом методов создаёт запись для каждого метода.
Новые маршруты, включая маршруты плагинов, обнаруживаются автоматически.

Ответ формируется из актуальной коллекции при каждом запросе и сортируется
по пути, затем по методу. `route` сохраняется в том же виде, что и в метриках,
например `/items/:id`, чтобы генератор мог использовать его в фильтре PromQL.
Каталог исключает `/health`, `/metrics` и `/handlers`. Его фильтр отделён от
фильтра метрик: запросы к `/handlers` продолжают учитываться гистограммой.

## Метрики запросов

Используется официальный [клиент Prometheus для Node.js](https://github.com/prometheus/client_js)
`@prometheus-io/client` версии `0.16.1`, преемник пакета `prom-client`.

Модуль `src/metrics.ts` подключается в `buildApp()` до регистрации маршрутов.
Каждое приложение получает собственный `Registry`, переданный в конструктор
гистограммы через `registers: [registry]`. Поэтому приложения в одном процессе
не смешивают измерения и не используют глобальный реестр.

Метрика `http_request_duration_seconds` имеет тип `Histogram` и измеряет время
обработки завершённого HTTP-запроса на сервере в секундах. Она записывается один
раз в общем `onResponse` из `reply.elapsedTime / 1000`. Сетевой путь до клиента
в это время не входит.

| Лейбл | Значение |
| --- | --- |
| `method` | HTTP-метод: например, `GET`, `POST`, `PUT` |
| `route` | Шаблон маршрута из `request.routeOptions.url`: `/items` или `/items/:id` |
| `status_code` | Итоговый код ответа: например, `200`, `201`, `400`, `404` |
| `pod` | Значение `POD_ID`, по умолчанию `local` |
| `datacenter` | Значение `DATACENTER`, по умолчанию `local` |

UUID и параметры query string не попадают в лейблы. Ошибки валидации `400`
учитываются, как и `404` для отсутствующей записи по `/items/:id`. Запросы
к `/health`, `/metrics` и неизвестным маршрутам исключены. Комбинация лейблов
появляется после первого учитываемого запроса.

Histogram экспортирует накопительные бакеты `_bucket`, число наблюдений `_count`
и сумму длительностей `_sum`. Бакеты можно суммировать по выбранным подам и
датацентрам, а затем вычислять квантиль. Это причина выбора Histogram:
готовые квантили Summary отдельных экземпляров нельзя корректно объединить
в общий квантиль. Подробнее: [Histogram и Summary](https://prometheus.io/docs/practices/histograms/).

Границы бакетов в секундах:

```text
0.0001, 0.00025, 0.0005, 0.001, 0.0025, 0.005, 0.01, 0.025,
0.05, 0.1, 0.25, 0.5, 1, 2.5, 5, +Inf
```

Дроби миллисекунды нужны для быстрых операций с хранилищем в памяти,
более широкие интервалы — для роста задержек под нагрузкой. Это начальный набор:
его нужно уточнить по реальным измерениям. Квантиль оценивается по бакетам,
поэтому точность зависит от их границ.

После нескольких CRUD-запросов метрики можно посмотреть в PowerShell:

```powershell
(Invoke-WebRequest http://localhost:8081/metrics).Content
(Invoke-WebRequest http://localhost:8082/metrics).Content
```

Пример p95 за последние пять минут, отдельно для каждого метода и шаблона
маршрута, с объединением выбранных подов, датацентров и кодов ответа:

```promql
histogram_quantile(
  0.95,
  sum by (le, method, route) (
    rate(http_request_duration_seconds_bucket{
      pod=~"pod-1|pod-2",
      datacenter=~"dc-1|dc-2"
    }[5m])
  )
)
```

Регулярные выражения в селекторах задают нужные экземпляры. `rate` применяется
до суммирования, чтобы учитывать сброс счётчиков при перезапуске каждого пода;
`le` сохраняется для вычисления квантиля. Результат выражен в секундах.
Порядок агрегации описан в [документации PromQL](https://prometheus.io/docs/prometheus/latest/querying/functions/#histogram_quantile).
Для графика нужны запросы к сервису и несколько успешных сборов Prometheus;
без наблюдений квантиль не определён.

## Генератор дашборда

Генератор состоит из четырёх модулей в `src/dashboard`:

| Модуль | Ответственность |
| --- | --- |
| `catalog.ts` | Получить `/handlers`, проверить ответ и вернуть массив `{ method, route }` |
| `dashboard.ts` | Построить модель дашборда из каталога без обращений к сети |
| `grafana.ts` | Сохранить модель через `POST /api/dashboards/db` и проверить результат |
| `cli.ts` | Прочитать окружение, последовательно вызвать модули и вернуть код завершения |

Модель использует datasource с UID `prometheus`, метрики с `job="items-service"`
и постоянный UID дашборда `items-service-overview`. На каждую ручку создаются:

| Панель | Запрос и единица измерения |
| --- | --- |
| Latency | p50, p95, p99 через `histogram_quantile` над `sum by (le) (rate(..._bucket))`; секунды |
| RPS | `sum(rate(..._count))` по выбранным экземплярам; запросы/с |
| Ошибки | `sum by (status_code) (rate(..._count))` для кодов `4xx` и `5xx`; ошибки/с |

Метод и шаблон маршрута берутся из каталога и экранируются как строковые литералы
PromQL. Переменные `${datacenter:regex}`, `${pod:regex}` и `$__rate_interval`
сохраняются в JSON буквально и подставляются Grafana при выполнении запроса.
При текущем интервале сбора `5s` минимальное окно `$__rate_interval` равно `20s`.

Селекторы `datacenter` и `pod` поддерживают несколько значений и `All`.
Список подов зависит от выбранных датацентров. Начальный выбор задан как
`current: { text: ["All"], value: ["$__all"] }`, а `allValue: ".*"` охватывает
все подходящие серии. Переменные обновляются при загрузке дашборда и изменении
диапазона времени (`refresh: 2`).

Генератор не ждёт появления метрик: он завершается сразу после успешного сохранения.
До первых наблюдений и сбора Prometheus списки переменных могут быть неполными,
а графики — пустыми. Выбранный `All` продолжит охватывать появляющиеся серии.
Фоновая нагрузка зависит от успешного завершения генератора через
`service_completed_successfully`.

В модели задано `editable: false`. Сохранение выполняется с `overwrite: true`:
повторный запуск обновляет дашборд с тем же UID. Массив панелей строится заново,
поэтому появившаяся ручка добавляет три панели, а исчезнувшая удаляет свои панели.
Сохранение и обновление описаны в
[API Grafana 12.2](https://github.com/grafana/grafana/blob/v12.2.0/docs/sources/developers/http_api/dashboard.md#create--update-dashboard).

Повторная генерация для уже работающего стенда:

```sh
docker compose run --rm --no-deps dashboard-generator
```

После изменения исходников генератора сначала пересоберите образ:
`docker compose build app-1`. Для запуска генератора непосредственно через Node.js:

```sh
npm run build
npm run dashboard:generate
```

Команда читает `.env`. Настройки генератора:

| Переменная | Значение по умолчанию |
| --- | --- |
| `APP_URL` | `http://localhost:8081` |
| `GRAFANA_URL` | `http://localhost:3000` |
| `GRAFANA_ADMIN_USER` | `admin` |
| `GRAFANA_ADMIN_PASSWORD` | Обязательна; берётся из окружения |
| `DASHBOARD_UID` | `items-service-overview` |
| `DASHBOARD_TITLE` | `Items service overview` |

В Docker Compose адреса заменены внутренними: `http://app-1:8080`
и `http://grafana:3000`.

## Фоновая нагрузка

Нагрузчик написан на TypeScript и работает в отдельном контейнере. Один общий
планировщик управляет частотой отправки: один слот означает ровно один HTTP-запрос,
включая создание записи, заполнение пустого пула и намеренную ошибку. Следующий
экземпляр выбирается по очереди только при фактической отправке запроса.

При настройках по умолчанию целевая частота зависит от времени с начала запуска:

```text
r(t) = 2 + 28 × min(t / 120, 1), t — секунды
```

Через 120 секунд нагрузка выходит на 30 RPS суммарно, примерно по 15 RPS
на экземпляр. Планировщик использует монотонные часы `performance.now()` и
не ждёт завершения предыдущего запроса. После задержки он пропускает просроченные
слоты, не накапливает очередь и не отправляет пропущенные запросы всплеском.
Пропуск из-за задержки или лимита параллельных запросов не расходует элемент
цикла операций и не переключает экземпляр. Автоматических повторов запросов нет.

Каждый экземпляр имеет собственный цикл из 100 операций:

| Операция | Число запросов | Ожидаемый ответ |
| --- | ---: | ---: |
| Корректный `POST /items` | 10 | `201` |
| `GET /items/:id` существующей записи | 43 | `200` |
| Корректный `PUT /items/:id` существующей записи | 43 | `200` |
| `POST /items` с пустым именем | 2 | `400` |
| `GET /items/load-missing` | 2 | `404` |

Операции распределены по циклу, поэтому оба экземпляра получают все три метода
и оба вида намеренных ошибок. Доля 4% относится к устойчивой работе: пока пул
пуст или восстанавливается, операции заменяются созданием записей. Эти запросы
отмечаются как `bootstrap` и учитываются отдельно при проверке пропорций.

Пулы содержат до 256 последних ID каждого экземпляра. ID добавляется только после
подтверждённого `201`; чтение и обновление выбирают ID из пула того же экземпляра.
Неожиданный `404` при обычном чтении или обновлении очищает его пул и увеличивает
номер поколения. Каждый запрос запоминает поколение при отправке: запоздалые
ответы старого поколения учитываются в статистике, но уже не очищают свежий пул
и не добавляют в него устаревшие ID.

Полученный результат сравнивается с ожидаемым. Например, `500` вместо запланированного
`404`, таймаут или сетевой сбой считаются неожиданным исходом. Место среди
незавершённых запросов освобождается при любом результате. В JSON-логах отдельно
показаны начатые и завершённые запросы, ответы по кодам, таймауты, пропущенные слоты,
текущая параллельность, ожидаемые и неожиданные исходы, заполнение пулов и устойчивая
работа. Фактический RPS считается по **начатым** запросам за монотонный интервал;
счётчики завершений не используются вместо частоты отправки.
`completed` включает все завершившиеся попытки, в том числе таймауты и отмену;
их причины показываются отдельными счётчиками. Счётчики в `total` накопительные,
а `actualRps` относится к интервалу между двумя отчётами.

Настройки нагрузчика через переменные окружения:

| Переменная | Значение по умолчанию |
| --- | --- |
| `LOAD_TARGETS` | `http://localhost:8081,http://localhost:8082` |
| `LOAD_START_RPS` | `2` суммарно |
| `LOAD_TARGET_RPS` | `30` суммарно |
| `LOAD_RAMP_SECONDS` | `120` |
| `LOAD_POOL_SIZE` | `256` на экземпляр |
| `LOAD_MAX_IN_FLIGHT` | `100` суммарно |
| `LOAD_REQUEST_TIMEOUT_MS` | `2000` |
| `LOAD_SHUTDOWN_GRACE_MS` | `3000` (допустимо от `0` до `3000`) |
| `LOAD_LOG_INTERVAL_SECONDS` | `10` |

В Compose цели имеют внутренние адреса `http://app-1:8080,http://app-2:8080`.
Для запуска через Node.js нужен работающий сервис:

```sh
npm run build
npm run load:start
```

Остановить только нагрузку, сохранив приложение и графики:

```sh
docker compose stop load-generator
```

Возобновить нагрузку при уже готовом остальном стенде:

```sh
docker compose up -d --no-deps load-generator
```

При остановке нагрузчик прекращает отправки, ждёт текущие запросы до трёх секунд
и затем отменяет оставшиеся. Внутренний срок завершения при настройках по умолчанию
укладывается в пять секунд, а контейнеру задан `stop_grace_period: 10s`.
После этого срока Compose может принудительно завершить контейнер; описание —
в [документации Docker](https://docs.docker.com/reference/compose-file/services/#stop_grace_period).

На плато успешные создания составляют около 3 записей в секунду, или 10 800 записей
в час суммарно. Хранилища сервиса растут до перезапуска: ограничение пула ID
ограничивает память нагрузчика и не удаляет записи из приложения.

## Разработка и проверка

Для разработки вне Docker нужен Node.js 24; версия окружения сборки закреплена
в Dockerfile и `.nvmrc`. Зависимости закреплены в `package-lock.json`.

```sh
npm ci
npm run check
npm run dev
```

`npm run check` проверяет типы приложения и тестов, выполняет контрактные
HTTP-тесты и собирает проект. `npm run dev` запускает сервер на порту `8080`
с перезапуском при изменениях. Переменные процесса: `PORT`, `POD_ID`, `DATACENTER`.

Проверка уже запущенного Docker-стенда: `npm run check:stack`.
Она проверяет API обоих экземпляров, независимость данных, каталог `/handlers`,
его учёт в метриках, `/metrics`,
готовность Prometheus, статус `UP` обеих целей, наличие собранных метрик
и автоматически созданный datasource Grafana. Она создаёт по одной тестовой записи.

Проверка генератора на работающей Grafana:

```sh
npm run build
npm run check:dashboard
```

Она проверяет повторное сохранение: два запуска оставляют один дашборд с тем же UID.
Изменение каталога проверяется на отдельном временном дашборде: новые ручки добавляют
панели, исчезнувшие удаляют их, пустой каталог удаляет все панели. Временный дашборд
удаляется после проверки. Модульные тесты построителя и HTTP-клиентов входят
в `npm run check` и не требуют работающего стенда.

Тесты нагрузчика проверяют пропуски без последующего всплеска, лимит параллельных
запросов, распределение операций между экземплярами, восстановление с запоздалыми
ответами и остановку. Устойчивую долю намеренных ошибок следует оценивать отдельно
от заполнения и восстановления пулов. Для реального прогона нужно дать нагрузчику
поработать 3–4 минуты: первые две минуты занимает рост частоты, затем проверяются
суммарный RPS, частота каждого пода и линии `400` и `404` в Grafana.

Автоматическая проверка реального прогона со стандартными настройками Compose:

```sh
npm run check:load
```

Она читает отчёты текущего запуска `load-generator`, дожидается отметки 240 секунд
и проверяет разгон, частоту отправок, смесь операций и метрики Prometheus.
Результат сохраняется в `output/load/verification.json`. Запросы для измерения
обращаются к Prometheus; дополнительную бизнес-нагрузку проверка не создаёт.

Реальный четырёхминутный прогон 30 октября 2026 года дал следующие результаты:

| Показатель | Результат |
| --- | ---: |
| Начатые и завершившиеся запросы | 5 381 |
| RPS на плато по Prometheus, окно 1 минута | 29,13 суммарно |
| RPS `pod-1` / `pod-2` | 14,56 / 14,56 |
| Намеренные ошибки в устойчивой фазе | 214 из 5 379 — 3,98% |
| Непредвиденные исходы / таймауты / пропущенные слоты | 0 / 0 / 0 |
| Начальное заполнение пулов | 2 запроса, включены в общий бюджет |

На обоих экземплярах выполнены все операции и получены оба кода ошибок.
В Grafana проверены линии `400` на панели ошибок POST и `404` на панели ошибок GET,
а также рост RPS с выходом на плато. У PUT намеренные ошибки не предусмотрены,
поэтому его панель ошибок может показывать `No data`.
Контейнер нагрузки остановился с кодом `0` за 0,64 секунды, после чего был запущен снова.

## Структура

- `src/app.ts` — HTTP API и хранилище.
- `src/handlers.ts` — автоматическое обнаружение маршрутов и `/handlers`.
- `src/metrics.ts` — отдельный реестр, гистограмма запросов и `/metrics`.
- `src/server.ts` — запуск сервера и обработка сигналов завершения.
- `src/dashboard/` — получение каталога, построение JSON, клиент Grafana и CLI.
- `src/load/scenario.ts` — циклы операций и пулы ID с номерами поколений.
- `src/load/scheduler.ts` — расписание роста частоты и пропуск просроченных слотов.
- `src/load/runner.ts`, `src/load/cli.ts` — выполнение запросов, статистика и остановка.
- `test/app.test.ts` — контрактные тесты.
- `test/metrics.test.ts` — контракт метрик, исключения и независимость реестров.
- `test/handlers.test.ts` — каталог, обнаружение новых маршрутов и изоляция приложений.
- `test/dashboard.test.ts`, `test/dashboard-http.test.ts` — построитель дашборда и HTTP-клиенты.
- `test/load-*.test.ts` — сценарий, расписание и выполнение нагрузки.
- `docker-compose.yaml`, `Dockerfile` — окружение запуска.
- `prometheus/prometheus.yml` — цели сбора метрик.
- `grafana/provisioning/datasources/prometheus.yaml` — datasource с uid `prometheus`.
- `scripts/check-stack.mjs` — проверка работающего стенда.
- `scripts/check-dashboard.mjs` — повторное сохранение и обновление состава панелей в Grafana.
- `scripts/check-load.mjs` — четырёхминутный прогон и сверка RPS/ошибок с Prometheus.

## Проверка полного запуска

30 октября 2026 года выполнен отдельный запуск из чистой копии исходников:
без локальных `node_modules`, `dist`, рабочего `.env` и сохранённых данных Grafana
или Prometheus. Файл `.env` получен копированием `.env.example`.
Для изоляции от основного стенда использованы отдельное имя Compose-проекта,
тег образа приложения, свободные порты и новые Docker volumes.

Генератор автоматически завершился с кодом `0`; создан один дашборд с девятью
панелями, `editable: false` и селекторами с множественным выбором и `All`.
Через **68,56 секунды** от начала команды запуска, включая сборку и ожидание
готовности, в Prometheus появились положительный RPS всех трёх ручек на обоих
экземплярах, оба кода ошибок на каждом поде и вычисляемый p99 для каждой ручки.
Повторный `docker compose up -d` сохранил один дашборд с прежним UID и девятью панелями.

Базовые Docker-образы к моменту проверки уже были скачаны. При первом скачивании
общее время запуска дополнительно зависит от скорости сети. Временные контейнеры
и volumes после проверки удалены; основной стенд продолжил работу.

Определение полей CRUD и поведение `PUT` выше — принятые решения для
неуточнённых в задании деталей. `/handlers` исключён из каталога, но учитывается
в метриках: в задании он не перечислен среди исключений из сбора метрик.
